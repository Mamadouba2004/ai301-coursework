# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded and consistent | The repro report's environment line/section, checked against the version/platform/OS the issue targets (issue body, repo-facts block) | The report names concrete environment facts (tool/library version, OS, relevant runtime versions), AND those facts either match what the issue targets or any difference from it is explicitly named and reconciled (e.g. "the issue is confirmed on latest/main; I tested v1.5.3, and here is why that still counts" — silence about a known deviation fails). Fails if the environment is unstated, or the tested version/platform differs from the issue's target with no acknowledgment at all. | required |
| Steps a stranger could actually follow | The repro report's steps/commands, judged against whether someone with no other access to the reporter's setup could carry them out | The steps are concrete commands or configuration runnable from a clean checkout or public environment, narrow enough to hit the exact trigger the issue describes (the specific flag, data shape, or platform detail it calls out as necessary). Fails if a step depends on a private or unshared resource (an internal monorepo, a config file not included), omits a parameter the issue names as essential to triggering the bug, or is vague enough that two different people running it could land in different places. | required |
| Artifact shows the issue's actual behavior | The output/log/error excerpt in the repro report, compared line-by-line against the specific symptom (error type, exit code, exact message, visual defect) the issue describes | The shown artifact demonstrates the same failure mode the issue reports. Fails if the artifact shows a different error type or exit code standing in for the reported one (a graceful validation error narrated as the reported panic), the tool merely running without producing the reported defect, a bug the issue does not describe, or a version/config difference from the issue's target presented as if it were evidence about the reported behavior — even when the report's prose says it matches. | required |
| Claimed outcome matches the evidence shown | The repro report's stated conclusion (reproduced, could not reproduce, root cause X), read against the artifacts actually included in the same report | Every claim of confirmation, certainty, or diagnosis is backed by a concrete artifact shown in that report. An honest "I could not reproduce this," backed by a real attempt and a stated hypothesis for the gap, passes exactly as well as a successful repro. Fails if the report asserts something is "confirmed," "guaranteed," or "verified" with no matching artifact, restates the issue's own description as if it were independently observed, or states an expected/actual pair that the shown artifact does not actually support. | required |
| Claim comment is specific, doesn't over-promise, and discloses AI use where required | The candidate claim comment's text, plus the repo-facts block's stated contribution and AI-use policy | The claim comment names the specific issue and a real next step in the commenter's own words — not generic flattery or interchangeable template language — and makes no promise of a fix, a timeline, or a guaranteed outcome. If the repo-facts block states an AI-disclosure requirement, the comment discloses AI assistance as that policy requires (course-authored comments are treated as AI-assisted for this check, so a strict disclosure policy is never satisfied by silence). Fails on boilerplate claim text, any promised deadline or guaranteed fix, or an undisclosed comment where the repo's stated policy requires disclosure. | required |

## Verdict rule

Accept only if all five required checks grade `pass`. If any required check grades `fail`, the verdict is `reject`. Treat `unclear` as `fail`: a claim of proof that cannot actually be verified from the available evidence is not proof ready to post, no matter how the other checks graded.

In live mode, on a claim-only draft (per SKILL.md), only the "Claim comment is specific..." check has evidence available; the other four report `unclear` / `not yet applicable: claim-only draft` and are excluded from the verdict, which then answers only whether the claim comment itself is ready to post.
