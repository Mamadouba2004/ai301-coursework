# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded and consistent | The repro report's environment line/section, checked against the version/platform the issue's own report or reproduction steps name as necessary (issue body, repo-facts block) | The report names concrete environment facts (tool/library version, OS, relevant runtime versions), AND those facts either match the version/platform the issue's OWN report targets, or any difference from that specific target is explicitly named and reconciled (e.g. "the issue is confirmed on latest/main; I tested v1.5.3, and here is why that still counts"). Judge only against the version the issue itself asks to be reproduced on — a version number some other commenter speculates about in the thread (a dependency theory, a "might be fixed by upgrading X" aside) is not a target this check enforces, and a report that doesn't chase down every such aside still passes. Fails if the environment is unstated, or the tested version/platform differs from the issue's own stated target with no acknowledgment at all. | required |
| Steps a stranger could actually follow | The repro report's steps/commands, judged against whether someone with no other access to the reporter's setup could carry them out | The steps are concrete commands or configuration runnable from a clean checkout or public environment, aimed at the exact trigger the issue describes (the specific flag, data shape, or platform detail it calls out as necessary). This check grades whether the attempt itself is concrete and repeatable — not whether it is guaranteed to have hit the trigger. An honest, well-described attempt that turns out not to trigger the bug still passes here; whether the report is honest about that outcome is the Honesty check's job, not this one. Fails if a step depends on a private or unshared resource (an internal monorepo, a config file not included), omits a parameter the issue names as essential to triggering the bug with no acknowledgment that it's missing, or is vague enough that two different people running it could land in different places. | required |
| Artifact shows the issue's actual behavior (or the honest result of a real attempt) | The output/log/error excerpt in the repro report, compared line-by-line against the specific symptom (error type, exit code, exact message, visual defect) the issue describes | When the report claims to have reproduced the issue, the shown artifact must demonstrate the same failure mode the issue reports. Fails a claimed reproduction if the artifact shows a different error type or exit code standing in for the reported one (a graceful validation error narrated as the reported panic), the tool merely running without producing the reported defect, a bug the issue does not describe, or a version/config difference from the issue's target presented as if it were evidence about the reported behavior — even when the report's prose says it matches. When the report instead honestly states it could not reproduce the issue, this check passes as long as a real artifact is shown for the attempt that was actually made (an output excerpt, a log, a rendered result) — it does not need to show the issue's own failure, since by the report's own honest account none occurred. | required |
| Claimed outcome matches the evidence shown | The repro report's stated conclusion (reproduced, could not reproduce, root cause X), read against the artifacts actually included in the same report | Every claim of confirmation, certainty, or diagnosis is backed by a concrete artifact shown in that report. An honest "I could not reproduce this," backed by a real attempt and a stated hypothesis for the gap, passes exactly as well as a successful repro. Fails if the report asserts something is "confirmed," "guaranteed," or "verified" with no matching artifact, restates the issue's own description as if it were independently observed, or states an expected/actual pair that the shown artifact does not actually support. | required |
| Claim comment is specific, doesn't over-promise, and discloses AI use where the policy explicitly asks for it | The candidate claim comment's text, plus the repo-facts block's stated contribution and AI-use policy | The claim comment names the specific issue and a real next step in the commenter's own words — not generic flattery or interchangeable template language — and makes no promise of a fix, a timeline, or a guaranteed outcome. Separately, read the repo's AI-use policy for which of two things it actually asks: (a) an explicit disclosure statement ("must state the tool used," "must be disclosed") — course-authored comments are treated as AI-assisted for this check, so this kind of policy is never satisfied by silence, and the comment must say so; or (b) that comments simply be written by a human in their own words / be understood and taken responsibility for, with no explicit disclosure line demanded — a comment that is already specific and not boilerplate satisfies this on its own, with no separate disclosure sentence required. A repo with no stated AI policy needs neither. Fails on boilerplate claim text, any promised deadline or guaranteed fix, or a missing disclosure statement specifically where the policy's own wording demands one. | required |

## Verdict rule

Accept only if all five required checks grade `pass`. If any required check grades `fail`, the verdict is `reject`. Treat `unclear` as `fail`: a claim of proof that cannot actually be verified from the available evidence is not proof ready to post, no matter how the other checks graded.

In live mode, on a claim-only draft (per SKILL.md), only the "Claim comment is specific..." check has evidence available; the other four report `unclear` / `not yet applicable: claim-only draft` and are excluded from the verdict, which then answers only whether the claim comment itself is ready to post.
