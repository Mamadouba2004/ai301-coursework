# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis grounded in the repro evidence | The plan's stated cause, read against every step, artifact, and control run in the repro-evidence block | The stated cause is consistent with everything the repro evidence shows: no control run, artifact, or step rules it out. Fails if the repro evidence itself contradicts the stated cause — a control run that still shows the symptom with the blamed mechanism absent or unchanged, an artifact showing the relevant state already resolved before the blamed step runs, or a step that isolates a different stage than the one the plan blames. A diagnosis the thread already favors is judged the same way as any other: agreement from other commenters is not evidence, and a confident thread consensus does not excuse ignoring what the repro evidence itself rules out. | required |
| Scope is one bounded change | The plan's scope statement (in-scope / not-in-scope, files or areas named), read against the issue's reported symptom | The plan names one bounded change that addresses the issue's reported symptom, with an explicit not-in-scope line (or equivalent) that excludes other work — including a deferred secondary fix the plan explains and scopes out on its own. Fails if the plan bundles the fix with broader or unrelated work the issue never asked for (a redesign, a migration, a new feature, a cross-cutting refactor, a new config option, a test-harness overhaul) even when the core fix buried inside it is correct. | required |
| A stranger could start executing it | The plan's approach / files-to-touch / order-of-work section | The plan names specific files, functions, or code locations and a concrete, ordered approach, such that someone with no access to the author's thinking could start making the change without asking a clarifying question first. Fails if real decisions are deferred to build time ("somewhere", "maybe", "upstream or vendored, whichever is easier", "not sure which layer"), if no file or area is named, or if the plan only describes investigating rather than a chosen approach. | required |
| Test plan is decisive | The plan's test plan, read against the repro evidence's own steps and artifacts | The test plan names a concrete, observable outcome tied to the repro evidence's own steps — re-running (or adapting) those steps and stating exactly what should be seen afterward that would not be seen before — such that the result conclusively shows the fix worked or didn't. Fails if the test plan names no observable outcome for the specific fix ("run the full test suite," "should feel fast," "nothing else should feel broken") or does not map onto the repro evidence's steps at all. | required |
| Plan comment matches the thread and the repo's stated conventions | The plan comment, read against the issue's thread highlights and the repo-facts block's stated contribution policy and AI-use policy | When the thread contains explicit maintainer direction (an owner-identified cause or location, or an approach the owner proposed or already validated), the plan comment engages with and follows that direction rather than pursuing an unrelated angle the thread has moved past. Separately, when the repo-facts block states an explicit AI-use disclosure requirement, the plan comment includes a disclosure statement; every plan comment graded here is course-authored and therefore AI-assisted, so silence never satisfies a stated disclosure requirement, no matter how good the plan is otherwise. A repo with no stated AI policy and a thread with no explicit maintainer direction needs neither. Fails on either miss alone. | required |
| Honest about real unknowns | The plan's stated risks/unknowns, and any `## Deviations` note, read against what the plan and test plan actually establish | Genuine uncertainties (an unmeasured cost, an untested platform variant, an open question about a related code path) are named as open questions rather than asserted as settled, and a recorded deviation states plainly what changed and why. This check is feedback, not a gate: a plan that is bounded, grounded, executable, and decisively tested does not need hedging it doesn't have to pass here. | preferred |

## Verdict rule

Accept only if all five required checks (Diagnosis, Scope, Executability, Test plan, Comms) grade `pass`. If any required check grades `fail`, the verdict is `reject`. Treat `unclear` as `fail`: a plan whose grounding, scope, executability, test plan, or thread/convention fit cannot actually be verified from the package is not ready to post and build from. The preferred Honesty check never changes the verdict either way — it is reported for feedback only.
